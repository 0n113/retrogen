# Retrogen Fabric 26.2 Review

Date: 2026-09-01  
Reviewed revision: `0c807c4` plus the local improvements described below  
Toolchain: Minecraft 26.2, Java 25, Fabric Loader 0.19.3, Fabric API
0.158.0+26.2, Fabric Loom 1.17.20

## Scope and method

The requested custom skill `minecraft262` was checked under user, project, and
organization scopes, including common spelling variants, but was not available
in this environment. The review therefore used the complete project source,
the resolved Minecraft 26.2 source JAR, Fabric API classes, previous
integration-test world, and a fresh dedicated-server smoke test.

The review covered build reproducibility, metadata, Mixin targets, normal and
retroactive population, structure suppression, feature filtering, queue
behavior, dimensions, command safety, config validation, state corruption,
write failures, restart behavior, and large-ledger risks.

## Implemented findings

### High: startup-loaded chunks were missed

Configuration and state were loaded on `SERVER_STARTED`, after server worlds
and persistent chunks were already live. Chunk-load callbacks occurring during
startup therefore returned while runtime state was null, and those chunks
could remain pending until a later unload/reload or manual retry.

The runtime now loads on `SERVER_STARTING`, before worlds are loaded. A
dedicated-server regression test confirmed that persistent chunks were queued
before the first tick and that the prepared target generated 347 coal ore
blocks without a manual retry.

### High: ledger write failure did not prevent mutation

The pre-generation in-progress marker called a best-effort save method that
logged `IOException` and returned. Generation would then continue without a
durable marker, defeating duplicate protection after a crash or restart.

The state store now exposes a strict save operation. World mutation begins only
after that operation succeeds. A new test makes the state directory
unwritable-by-construction and verifies that the strict operation throws while
the in-memory in-progress marker remains intact.

### High: duplicate pass IDs silently skipped work

Two configured passes could share one ID. Because completion is keyed by pass
ID, the first pass could mark the chunk complete and silently suppress the
second pass even if it selected different features.

Validation now rejects duplicate IDs and null pass entries during startup.

### Medium: worldgen caught every `Throwable`

Catching `Throwable` also swallowed JVM-level errors such as
`OutOfMemoryError`, potentially allowing a severely compromised server to
continue. The generation boundary now catches `Exception`; JVM errors propagate
while the already-persisted in-progress marker prevents an automatic duplicate
pass after restart.

### Medium: unloaded command targets were reported as queued

An explicitly addressed unloaded chunk was added to the volatile queue and
dropped on the next tick because `getChunkNow` returned null. The command still
claimed it was queued.

Retry and clear now persist the pending state and report that execution waits
for the next chunk load. They do not retain a pointless in-memory queue entry.

### Medium: conflicting ledger markers could survive normalization

If a manually edited or previously damaged state contained both `completed`
and blocked markers for one chunk, calling `markComplete` did not remove the
blocked markers when the completion index already contained the chunk.
Completion now always removes conflicting failed and in-progress entries.

### Low: moving build target and broad game predicate

The project used `1.17-SNAPSHOT`, even though builds resolved to Loom 1.17.20,
and declared `~26.2` in mod metadata. This reduced reproducibility and could
admit an untested later 26.x Minecraft version.

Loom is now pinned to 1.17.20 and metadata requires exactly Minecraft 26.2.

### Low: boxed completion index

The JSON representation remains string-based for readability, but its runtime
index used boxed `Long` objects. It now uses FastUtil `LongOpenHashSet`, reducing
per-chunk heap overhead without changing the state schema.

## Remaining risks and recommended next work

### High: full JSON rewrite for every pass start

Crash safety currently requires persisting an in-progress marker before each
world mutation, and each persistence serializes the complete ledger. As the
world approaches hundreds of thousands or millions of completed chunks, this
becomes an \(O(n)\) write for every new pass execution and can create severe
tick stalls.

Recommended direction: introduce a schema-v2 sharded ledger, such as one file
per dimension/pass and region, or a compact append-only journal with periodic
checkpoints. Keep migration from schema v1 explicit and backup-safe.

### Medium: deferred 3x3 entries have no backoff

When `requireLoaded3x3` is enabled, a chunk with missing neighbors is removed
and re-added every level tick. A large deferred queue can consume the configured
processing budget continuously without making progress.

Recommended direction: move blocked chunks to a deferred set and wake them from
neighbor chunk-load events, or retry them at a configurable low-frequency
interval.

### Medium: queue count is dimension-wide

`/retrogen status <pass>` prints the complete dimension queue length, not the
number of queued chunks still pending for that specific pass. With multiple
passes, the displayed value can therefore be misleading.

Recommended direction: calculate a pass-filtered queue count or label the
current field `dimensionQueued`.

### Medium: no state repair or inspection command

Administrators can see only aggregate counts. Recovering a large set of failed
or in-progress chunks requires manually editing JSON, which is risky while the
server is stopped and impractical at scale.

Recommended direction: add paginated `list-failed`, `list-in-progress`, and
backup-producing repair/export commands before adding bulk clear operations.

### Medium: atomic rename is not power-loss durability

Temporary-file plus atomic rename protects against a partially replaced JSON
file, but neither the file nor parent directory is explicitly `fsync`ed. A host
power loss can still lose the latest rename on some filesystems.

Recommended direction: force the temporary file before rename and, where
supported, force the parent directory afterward. Retain world-level backups as
the primary disaster-recovery mechanism.

### Low: deprecated `WorldGenRegion#getLevel`

Minecraft 26.2 marks the only direct `WorldGenRegion` server-level accessor used
by the natural-population hook as deprecated. It remains present and passed the
dedicated-server test. Replacing it with a private-field accessor Mixin would
remove the compile warning but increase mapping fragility, so no change was
made in this pass.

### Low: runtime config reload is unsupported

Changes require a clean server restart. This is operationally safe but slows
iteration and can surprise administrators expecting `/reload` to apply the
file.

Recommended direction: either document restart-only behavior more prominently
or add a validated `/retrogen reload` that refuses changes while work is queued
or in progress.
